# Character special rooms ("character attribute keys") of the dungeons

Research for the native port (2026-10-19). Read-only study of `work/decomp/all_dun.c` (Ghidra decompile of SCUS_971.11 + overlays), jump tables and branches re-disassembled with `work/disasm.ps1`
(`DisasmForce.java`, `DumpBytes.java`), the seven `dun/script/d0N/event.stb` scripts (`work/d0N_event_dis.txt`, message banks cut out of the stb), the dungeon `.cfg` files (`data/dun/*.cfg`, Shift-JIS)
and the part models (`data/dun/mpd_pack/*.mpd`). Tags: **READ** (decompile/disassembly), **VERIFIED-DATA** (read from a file/table), **INFERRED** (reasoned, not proven).
Companions: `notes/dungeon_events.md` (event engine, ext table), `notes/native-plan.md` (generator port). Not duplicated here: back floors (`back_floors.md`), EB duel (`eb_duel.md`).

## 0. The short version

* There are **two** mechanisms that put character rooms on a floor, both inside `CDungeonMap::BuildCharaSpecialParts` (0x1ca480, called from `buildRandomMap` 0x1cb670 only for a *fresh* floor, after `GetRoomLinkInfo`):
  1. **Random extra rooms** on ordinary floors (zone `UserStatus+0x8b10` outside 0..5): a cascade of dice rolls, gated by the number of party members that have joined (`UserStatus+5`), the dungeon (`selectMapNo` 0..5, **never d07**) and the floor (`UserStatus+2`).
  2. **Forced-character floors** (the floor script calls `_SET_MAIN_CHR2(c)` + `_SET_LIMMIT_ZONE(c)` before `_SET_RANDOM_MAP`): `SetCharaDoor(this, c)` (0x1cb230) puts exactly that character's room on the floor, always (see section 3).
* A character room is simply a **cfg part** (number 59..69) written into the cell grid (replacing a straight corridor cell, or a room-door cell). The generic `CDungeonEventMan::SetupEvent` (0x1ccf40) then creates one event slot per marker of the part; nothing is special-cased. Part 55..58 ("Xiao 1", big rooms, `u01`) is **never** generated (dead code; the cfg comment "シャオパーツまだ出ず" = "Xiao parts not yet appearing" refers to them).
* Scripts: 350/351 Xiao jump gap (OK button, Xiao only), 360/361 Goro switch (hit with Goro's weapon), 365/366 Ruby crystals (hit with a Ruby shot of the right element), 370 Ungaga black wind (hit with Ungaga's blast), 375 Osmond gap (**message only**). Wrong character: a hint/refusal message. d07 has no scripts for any of them.
* Port state: the *layout* part is ported (random branch exactly, forced branch only draws the dice); `PT_HIT_MARKER` is not parsed, the object-handle externs (1030..1035) and the ruby key do not exist, and `poll_script_markers` skips 350..375. Details and order in sections 8 and 9.

### 1.2 Marker syntax and fields (READ, `TEIGIAnalyz` 0x1ce090, all_dun.c 115030-115110)
```
PT_MARKER     "name", radius, event_id, item_use, auto, switch, ext     -> def: +0x18 radius, +0x20 event, +0x28 item_use, +0x24 auto, +0x2c = -1, +0x30 = -1, +0x34 switch, +0x38 ext
PT_HIT_MARKER "name", radius, event_id, chara_id, attack_id, switch, ext -> def: +0x18, +0x20, +0x24 = 0, +0x28 = 0, +0x2c chara, +0x30 attack (-2 -> BtRubyDoorKey), +0x34, +0x38
```
(`+0x1c` = the part number, `+0x10/+0x14` = the part frame and the named empty frame found with `SearchFrame`.) The character-room markers all have `OFF OFF ON OFF` = no item use, not automatic, **switch ON**, normal (not heavy) event. So they are live from the moment the slot exists.
`chr<c>_<k>`: `c` = character index 1..5 (Xiao 1, Goro 2, Ruby 3, Ungaga 4, Osmond 5), `k` = running number inside the part. The name is only the name of an **empty frame** in the part's collision mesh (`d0Nu0X_a.mds`, objects without mesh); the scripts address those frames by name (`_GET_OBJHDL`), the engine uses their world position for the trigger area.

### 1.3 SetupEvent (READ, 0x1ccf40)
For a random floor (`param_3 == 1`): for each of the 16 x 16 cells with a part, for each of the 0x40 event definitions whose part id (`def+0x1c`) equals the cell's part: take a free slot of the 0x60 (`SearchDataSlot`), `Set__17CDungeonEventData` (0x1cc820: `slot+0x30 = def+0x28`, `slot+0x34 = def+0x34` (switch), `slot+0x38 = 1`, `slot+0x3c = -1`), build the part rotation from the cell and part rotation, place the frame, `GetWorldPosition` -> slot `+0x10` (marker world position), slot `+0x20` = (0, atan2(...), 0, 1) (heading). Fixed maps (story/boss, `param_3 != 1`) create the slots for every part once. `_SET_EVENT_SW(id, on)` -> `SearchDataSwitch` (0x1cc990) sets `slot+0x34` of **every** slot whose def event id equals `id`.

## 2. BuildCharaSpecialParts: the random extra rooms (READ 0x1ca480; ported in `dungeon.cpp::build_chara_special_parts`, verified identical to the decompile)

Inputs: `selectMapNo` m (0..5 = d01..d06; `m >= 6` returns at once, so **d07 never gets a character room**), `UserStatus+2` = floor f (0-based), `UserStatus+5` = party size p (number of characters that have joined), `UserStatus+0x8b10` = zone z. Only when z is **not** in 0..5. Rolls v = `(int)(rand() * 100.0 / 2^31)` (0..99).
The cell lists come from `CreatPartsList(list, 0x40, lo, hi)` (0x1ca290): scanning y,x = 1..14 (row by row), `hi == -1`: cells whose part == `lo` **and** none of their 4 neighbours is a link/locked-door cell (flag 0x400); otherwise cells with `lo <= part <= hi`; at most 63 entries. One random pick `list[(int)(n * rand() / 2^31)]`.

1. **Xiao 2 gap** (all of m = 0..5): v1 = first roll; `if (m == 0 && f < 8) v1 = 0`. If `p > 1 && v1 > 50` and the list of straight corridor cells (`lo = 0, hi = -1`) is not empty: that cell's part := **0x3b (59)**. (49 %.) d01 therefore only from floor index 8 on.
2. Second roll v2 (always drawn), then by dungeon (cascade: each test is only reached when the one above failed, including "list empty"):

| m | rule (doors = `CreatPartsList(9, 12)`) |
|---|---|
| 1 (d02) | `p > 2 && v2 > 10 && f > 8 && doors`: door part += **0x33** (Goro) |
| 2 (d03) | `p > 2 && v2 <= 39 && doors` -> Goro (+0x33); else `p > 3 && v2 > 39 && f > 8 && doors` -> Ruby (+0x37) |
| 3 (d04) | `p > 2 && v2 <= 19 && doors` -> Goro; else `p > 3 && v2 <= 39 && doors` -> Ruby; else `p > 4 && v2 > 39 && f > 8 && corridor list` -> part **0x44** (Ungaga) |
| 4 (d05) | Goro `p > 2 && v2 <= 9`; else Ruby `p > 3 && v2 <= 19`; else Ungaga `p > 4 && v2 <= 29` (corridor list); else Osmond `p > 5 && v2 > 40 && f > 7` (corridor list) -> part **0x45** |
| 5 (d06) | as d05 but the Osmond test has no floor condition (`p > 5 && v2 > 40`) |

Door parts keep their rotation variant because the offset is *added* (9..12 + 0x33 = 60..63, + 0x37 = 64..67); corridor-type parts (59, 68, 69) are written absolutely and the cell's `rot` (0/1) stays. So the room is always exactly where an ordinary corridor cell / room door was: entrance and exit are the two ends of the corridor cell (Xiao, Ungaga, Osmond: a gap/obstacle in the middle of a straight corridor) or the door of a room (Goro, Ruby: the door only opens after the switch). INFERRED for what lies behind: nothing is guaranteed to be on the only route, the rooms are optional shortcuts/detours (Goro/Ruby close a room door, the rest cut a corridor; the layout is a spanning structure with loops, but I did not prove a floor can never be blocked).
Resulting chances: d02 89 % (floor > 8, Goro joined); d03 40 % Goro / 60 % Ruby; d04 20 / 20 / 60 % Goro/Ruby/Ungaga; d05/d06 10 % Goro, 10 % Ruby, 10 % Ungaga, 11 % nothing, 59 % Osmond (when everybody has joined). Each also needs a non-empty list. Port code matches these thresholds (checked against the decompile line by line).

## 5. How the engine raises these events (READ, `MoveChara` 0x1db08a0, `CDungeonEventMan`)

Slot layout: `slot+0x00` def pointer, `+0x10` world pos, `+0x20` heading vec, `+0x30` copy of def item-use, `+0x34` switch, `+0x38` alive (1), `+0x3c` "last character who got the hint" (-1 at creation). `CheckSwitch` (0x1cc880) = def != 0 && `+0x38 != 0` && `+0x34 != 0`.

**A. OK press (`SearchDataSlotPos2`, 0x1ccde0; MoveChara all_dun.c 177425)** guarded by `DAT_01dc44e4 != 0 && DAT_01dc4518 == 0` (player free). First slot (in slot order) that passes `CheckSwitch`, `|marker.y - player.y| < 40` and `dist(marker, player) <= radius + 10`. Then:
```
if (slot && def.chara != -1 && slot.+0x3c == UserStatus.character) slot = 0;     // this character already read the hint here
if (slot && def.event != -1) { heavy = def.+0x38; DAT_01d56764 = 0; eventId = def.event; save marker pos/rot }
if (eventId != -1) {
   if (def.chara != -1 && OK down) { if (UserStatus.character == def.chara) slot.+0x3c = UserStatus.character; gameTask = 400; DAT_01d567f4 = 1; }   // _CHECK_CHR_HELP = 1
   if (def.auto) { fade 120, gameTask = 500 }
   else if (slot.+0x30 && Down(0x80)) { gameTask = 400; mode = 2 }
   else if (Down(OK)) { gameTask = 400; mode = 1 }
}
```
Plain markers (`PT_MARKER`, chara -1: Xiao/Osmond) simply run the script with action mode 1 on an OK press; `_CHECK_CHR_HELP` is not consulted by 350/351/375. For hit markers the OK press is only a **hint request** (`DAT_01d567f4 = 1`). The `slot+0x3c` memory means: the matching character gets the hint once, then OK near the marker no longer opens the event so that character's attack (same button) is not swallowed; every other character gets the hint message on every OK press (and cannot attack there). INFERRED intent, READ mechanics.
**B. Hit detection (`SearchDataSlotPos` -> `CheckCollisionDataHit`, 0x1cccd0 / 0x1ccba0; MoveChara 176526)**, every frame while playing (skipped while `Down(0x10)` is held unless the player is dead or idle-and-attacking; INFERRED: "not in first-person view"). For each slot passing `CheckSwitch`: a plain slot (`def.chara == -1`) within `dist <= radius` of the player is returned first and then discarded by the caller (so a plain marker can shadow a later hit marker); a hit slot is matched against the 0x60 `NowColData` hit spheres (`CCollisionData`, stride 0xa0, used flag at `+0x3c00 + 4i`): `def.chara == sphere.+0x58` and (`def.attack == -1` or `def.attack == sphere.+0x60`) and `DistVector(sphere.pos, slot.+0x10) <= def.radius` (3D, no y test). Hit -> `DAT_01d567f4 = 0`, action mode 1 (`DAT_01d56764`), heavy = `def+0x38`, event = `def.event`, `gameTask = 400` (event starts at once, no fade).
The spheres are the ones the player's code registers: `+0x58` = owner kind, `+0x60` = sub id:
* Goro: `GoroKey_Play` 0x244130 -> `basic_damage(0, 2)` (all_dun.c 169514): chara 2, attack 0. Marker accepts any attack of chara 2 (`-1`).
* Ruby: `BattleActionShotRuby` 0x1dbcf80 -> `CSHOT_EFFECT::Set(..., 3, uVar1, ...)` with `uVar1 = byte NowWeaponHave+0x16` = the weapon's chosen element (0 fire, 1 ice, 2 thunder, 3 wind, 4 holy; UserStatus `element_choice()`), registered by `CSHOT_EFFECT::Step` each frame as a sphere (+0x58 = 3, +0x60 = element). The marker's attack id is `BtRubyDoorKey` (below), so the shot must carry the right element.
* Ungaga: `UngagaKey_Play` 0x243260, state 0xe (OK held; every 30 frames) -> `CSHOT_EFFECT::Set(..., 4, 2, ...)` (all_dun.c 169407): chara 4, attack 2 = his blast. His melee (`basic_damage(0, 4)`) does not match.
* Toan/others: chara 0 / 1 / 5 spheres exist but never match a character-room marker.
The port already has all of this data: `ColEntry::owner_kind` / `sub_id` (`combat.h`), set in `player_attack*.cpp` (Ruby `element_choice`, Ungaga `owner_kind 4 / sub_id 2`, Goro `owner_kind 2`).

**BtRubyDoorKey** (`TEIGIAnalyz` start, all_dun.c 114198): `BtRubyDoorKey = (int)(rand() * 5.0 / 2^31)` (0..4, clamped to 0); `if (selectMapNo == 2 && UserStatus[2] == 8) BtRubyDoorKey = 0;` (the d03 story floor). It is picked **when a cfg is (re)parsed**, i.e. when `BtMapJumpLoad` (0x1b20e0, `_LOAD_DUNGEON_MAP2`) sees a cfg name different from `BtCfgCash` (cleared by `BtMapJumpCashClear` 0x1b20c0 on dungeon entry) -- not per floor: every floor of the same `main_a` cfg keeps the same Ruby colour. The `-2` of `PT_HIT_MARKER` is replaced by the key at parse time. `_GET_RUBY_ELEMENT` 0x1bd010 returns it, `_SET_RUBY_ELEMENT` is a no-op. The `rand()` call also advances the global generator that `buildRandomMap` draws the next floor seed from (one extra draw per cfg parse, before the seed draw; the port's `start_floor` does not model it).
Colour <-> element (VERIFIED by the crystal internal function in d03: `red_on` handle for 0, `blue` 1, `yellow` 2, `green` 3, `pink` 4).

## 7. Ability gates in play (summary)
* The active character is `UserStatus+4` (`_GET_NOW_USER_ID`, 0 Toan .. 5 Osmond). The other party members are not on the field (the ring menu swaps the character), so "what happens to the party" is: nothing; only the active character is moved/placed. On forced floors the character is swapped by the script and the swap menu is refused (zone 0..5).
* Xiao: stand within radius + 10 (= 16) of `chr1_3/4` (|dy| < 40), press OK (cross, 0x40), must be character 1; 186-frame jump scene; lands 120 forward of the marker; others get 1900 + id and stay.
* Goro: the hit must come from a `CCollisionData` sphere with owner 2 within 8 of `chr2_0/1` (hammer swing); the OK hint only explains. Success disables both markers for the floor and raises the door (the door collision frame moves up 40; it never closes again).
* Ruby: a Ruby shot with weapon element == key within 3 of the crystal marker; Ruby may need to equip a weapon of that element first (hint says "react with some spell"). Wrong element: nothing happens (no message).
* Ungaga: his charged blast (owner 4, attack 2) within 13 of `chr4_2` (centre of the part). Others: hint 2200.
* Osmond: message only.
* The frames (doors, switches, crystals, mist NPC) are addressed by name; the engine moves collision frames, so passing a door is a matter of collision, not of a flag.
