# Native port plan (engine decided 2026-10-18: Godot 4 front end + standalone C++ logic library `dccore`)

Reasons: assets are built from the player's disc at runtime (no editor pipeline needed), logic comes from decompiled C so C++ ports most directly, Godot is text-based/headless/CLI-friendly and open source, escape hatch = swap the front end later.

## Milestones (each ends with something visible and a go/no-go check)
0. **Tooling**: Godot 4.7.x (standard, not .NET), Visual Studio Build Tools (C++), CMake. Hello-world GDExtension that links dccore.
1. **Assets**: C++ readers for pack/IMG/TIM2/MDS/WGT verified against Python; first-run converter from the user's ISO/DATA.DAT to a cache folder; Godot shows a Toan model (original, then new) with a basic skeleton.
2. **Animation**: decode `.mot` (+ `MotionProc2` key tables, `base.cfg` motion numbers); play idle/run/attack in Godot.
3. **Dungeon floor**: parse map collision (`_a`) and camera (`_v`) meshes, dungeon `.cfg`, floor generation from the seed (`CDungeonMap`); walk a whole floor with correct collision and camera. **GO/NO-GO CHECKPOINT.**
4. Monsters: `.stb` script VM (`CRunScript::exe`), `CMonstorUnit` rules, combat/damage (`CheckDmg`), items and weapons.
5. Town/Georama (`CEditGround`/`CEditArea`, `.scn`), menus, text (`.mes`), save files.
6. Sound (Sony SEQ/VAB-style), opening scenes, co-op networking (native, replaces the PINE hooks), modern lighting pass.

Reference data: `notes/native.md` (survey), `notes/symbols.csv`, `work/decomp/all_dun.c` (raw decompile of everything), Python format tools in `tools/dc`.

## Milestone 2 (animation): DONE, verified against the running game (2026-10-18)
Everything below was decoded from the game's own code (decompile in `work/decomp/all_dun.c`: `MotionProc`, `MotionProc2`, `SetMotionEX`, `CreateAnimeDataEX`, `QuatToMat`, `QuatSlerp`, `CommandMOTION/KEY`) and then checked numerically against live memory in PCSX2 over PINE.
- **`.mot`** = the same record chain as `.wgt`: 0x20-byte header `{object, param, type, unk, count, more, ...}` + `count` keys of 0x20 bytes: **time = u32 frame number at +0** (it is NOT a float; the decompiler's float casts hide that), data vec4 at +0x10. Track types: 0 rotation, 1 scale, 2 translation (applied to local matrix: rotation rows 0..2, translation row 3), 0xc vertex animation, 0x1e/0x1f camera position/target, 0x20/0x21 camera roll/FOV, 0x28/0x29 material animation, 0x32/0x33 visibility flags, 200 = skip. Tracks reference the MDS object (= frame) index.
- **Rotation key** = quaternion stored (w, x, y, z); the game **negates w** (i.e. uses the inverse rotation), slerps (acos/sin when `1-dot > 0.001`, else linear; shorter arc by negating the second key when dot < 0), no renormalisation, then `QuatToMat` writes rows 0..2 of a row-vector matrix. Factor `f = (t - t0)/(t1 - t0)` between the keys around `t`; `f <= 1e-4` uses key 0, `f >= 0.9999` uses key 1.
- **Hierarchy**: world = local x parent_world (row vectors) over the MDS parent indices. `.bbp` = one local bind matrix per object (a chain, same convention). Some `.bbp` entries are all zero (Xiao's dummy root, every rigid part): treat as identity.
- **Skinning** (`MotionProc2`) is plain additive linear blend skinning in percent: `p' = p + sum_b (w_b/100) (p * B_b^-1 * A_b - p)`, B = bind world, A = animated world, **both chains taken relative to the skin object's parent (that object is identity)**; the game then draws the skin through the parent's world matrix, so in a renderer with full-world bone poses the parent's matrix cancels and only the binds (`inverse(B_b * inverse(B_root))`) need the root.
- **Timing**: `KEY start,end,speed` in `base.cfg` = frame range and frames advanced per game tick; the game ticks 60 times per second (measured: speed 0.05 -> 3.00 frames/s). At run time the game rewrites some entries (7 of Toan's 41: idle 0.05 instead of 0.2, walk/attack-stance speeds follow movement). Playing wraps with `time -= end - start` when `floor(time) >= end`.
- **Verification**: `native/tools/pose_diff_live.py` (all joint local matrices vs the game, exact time forced by freezing the motion via `CCharacter+0xC64 |= 1` and opening the playing motion's table entry) and `native/tools/check_skin_live.py` (every skin vertex vs the game's vertex buffer: `frame+0x260` = visual, `visual+0x20` = MDT, vertices at `MDT+0x40`). Results: Toan, new Toan-era pose matrices equal to 1e-3 at 6 random times; **skinned vertices equal to 1e-5 for all 403 (Toan) and all 1,210 (our new Xiao) vertices at 7 / 3 times**. `native/tools/pose_regression.py` is a tripwire (CRC of poses for 5 characters).
- **Godot**: `DcCharacter` node (`native/gdext/src/dc_character.*`): Skeleton3D with one bone per MDS object driven by `set_bone_global_pose`, GPU-skinned body (4 bones per vertex, binds per skin root), rigid parts as `MeshInstance3D` set to their bone's world matrix each frame; `play(motion)`, `set_time(frame)`, `_process` advances at the game's rate. `native/godot/main.gd --motions 0,1,11,6` renders screenshots. All four new characters (Toan, Xiao, Ruby, Ungaga) animate correctly; stock Toan too.
- Not yet done: motion blending (`state[2]` transitions), visibility tracks, vertex-animation tracks (type 0xc), cloth (`.clo`), Goro's textures (see Milestone 1 open items), face expressions (`TEX_ANIME`), per-motion runtime speed rules, weapon attachment points (`weapon`/`item` objects exist as joints).

## Milestone 3, phase A (dungeon floor generation + rendering): DONE, verified against the running game (2026-10-18)
- **Generator** = `native/dccore/src/dungeon.cpp` (`build_random_map(seed, rooms, map_no, fresh, state)`), a port of `CDungeonMap::buildRandomMap` and everything it calls (`buildRoom`, `joinRoom`, `setRoomObject`, `setRoomDivid`, `setUnderDungeonStart`, `setStair`, `mapPartsFilter`, `GetRoomLinkInfo`'s layout part, `SetUnderLoad`'s filler column). The game uses the libc `rand()` (32-bit LCG `s = s * 0x41C64E6D + 0x3039`, returns `s & 0x7FFFFFFF`, state at `*(_impure_ptr)+0x58`), so a floor is a pure function of its seed; a fresh floor draws `seed = (int)(rand() / 100000.0f)` first and `srand(seed)`s it.
- **Float details that matter**: every pick is `(int)((float)n * (float)rand() / 2.1474836e9f)` (the literal is exactly 2^31 as a float) and the PS2 FPU **rounds toward zero**; the port computes each operation exactly in double and truncates to float (`to_float`, switchable with `set_dungeon_round_to_zero` for experiments).
- **Decompiler trap**: the decompiler writes neighbour cells as `&DAT_xxxx + cell*0x4c` where DAT_xxxx = field +/- 0x4c, which silently means "the cell to the right/left". `joinRoom` puts a horizontal door flag on the room's own edge cell this way; reading it as the cell outside the room cost two bugs. Always convert a DAT_ offset back to (field, +/- 1 cell).
- **Hidden state**: GetRoomLinkInfo's 16x16 `scanRoomInfoWork` array (0x01D569A0, 1 KB) sits directly in front of the 20x20 cell array (0x01D56DA0, 0x4c bytes per cell), so "the cell above" a row-0 cell reads one of its entries (or earlier memory). That decides whether a start can be at y=0 and differs between floors depending on the previous GetRoomLinkInfo run. `GenState` carries it; the port reproduces it exactly when fed the same state.
- **Not ported yet** (layout unaffected): the treasure box GetRoomLinkInfo places with the link door (needs `SearchiDoPutArea` + the room floor polygons `ItemFreeAreaAll`; the port assumes the first position is accepted, so the game's rand state afterwards differs), `BuildCharaSpecialParts` (needs `UserStatus` fields; only active from floor 8 on for map 0), `buildDummyModel` (map 4), `buildEventData`, `SetCharaDoor`.
- **Verification**: `tools/dc/validate_gen.py` sets the game's rand state with `srand`, calls the game's own `buildRandomMap(MainDungeonMap, rooms, 1)` through the hook mailbox (`coop/hooks.py`, update phase) and compares seed, room list, every cell's (part, rot) and the scan array with `native/build/core_release/dcdungeon.exe`: **230 of 230 random floors identical** (2..12 rooms; the run then stopped because the live game had been rebuilt too often and left the dungeon scene, the emulator was restarted from state 1 afterwards). Regression test `test_dungeon` pins 8 of them. `tools/dc/dungeon_live.py` compares whatever floor is currently live.
- **Pieces**: floor pieces, their collision (`_a`) and camera (`_v`) meshes and the shared texture container are in `dun\mpd_pack\<dungeon>.mpd` (e.g. `d01main_a`), the part table in `dun\<dungeon>.cfg` (`DEF_PATS` blocks; the block index is the part number in the grid; `PT_BASE "file", slot, x,y,z, rot`, `PT_COLS`, `PT_CAM`, `PT_FIRE` torches, `PT_MARKER` events, plus environment lines `AMBIENT`, `LIGHT_C dir(towards the light) colour(128 = full)`, `FOG near,far,r,g,b`, `BG_COL`, `URA_*` for the back floor, `GRD_IMG`). `dccore/floor.*` parses all of it. Placement (`CDungeonMap::DrawMap`, `CDungeonParts::Draw`): cell (x, y) at world (x*160, 0, y*160); each model at that position plus its PT_BASE offset, rotated about +Y by `-90 * i` degrees with `i = turn(cell_rot + model_rot)`; the game wraps `i > 3` to `i - 3` and `3` to `-1` (`model_turn_index`). The chain-table rotations (corner masks) confirm the direction.
- **MDS**: visual pieces with a colour block store it after the UVs, so `parse_mds(data, strict=false)` skips the block-overlap check (the byte-exact writer in `tools/dc` still uses the strict one); all 91 visual pieces of d01main_a now parse. Collision/camera meshes fail with "negative tuple count": a different layout, decoded in phase B.
- **Godot**: `DcDungeon` node (`gdext/src/dc_dungeon.*`), `DcModels.build_dungeon(name, seed, rooms, map_no)`, viewer `native/godot/floor_view.tscn/.gd` (`--cfg d01main_a --seed 8097 --rooms 6 --views overview,start,x:y:z>x:y:z --lit 0|1 --out prefix`). The floor of seed 8097 renders recognisably (rooms, corridors, dividers, cave walls). Lighting is a first guess (not yet compared with the game): lights point towards the cfg vector, energy 255/128. The last column (part 0x2c, a filler) shows as a thin strip at the edge.
- Next: phase B (collision `_a` + camera `_v` decoding, controller, follow camera: walk a whole floor).

## Milestone 3, phase B (collision, movement, camera): C++ port verified against the running game (2026-10-18)
- **Collision data**: a `*_a.mds` (movement) / `*_v.mds` (camera) piece is an MDS container; each mesh object has a normal MDT header but a special group list: after the 16-byte group header come `{type, count}` and `count` polygons of five ints `{v0, v1, v2, attribute index, spare}` (no material word); vertices are vec4 at +h[4]; attributes are 16-byte records at +h[14] (the 16-bit value at attribute byte 6 is the type mask the queries filter on: `(type & mask) == 0` -> considered). The game turns them into `CCPoly` (0x50 bytes: v0,v1,v2 as vec4, normal = (v1-v0) x (v2-v0) NOT normalised, attribute) and `CFrame::PickUpNearPoly` returns those overlapping a box, transformed by the frame (SetRotation y = -90 deg * turn, SetPosition = cell * 160). `dccore/collision.*`, `floor.*` (`floor_polys_near`, `floor_camera_polys`). Check: `tools/dc/validate_polys.py` compares the polygons per cell with the game's own PickUpNearPoly (all 102 cells of the live floor identical: positions, normal direction, attribute; the camera pieces match in 92 of 93 cells, the exception is the exit-stair piece where the game leaves out some objects).
- **Queries ported** (`collision.cpp`): `CheckHit` (segment vs polygons: first hit or nearest; bbox prefilter, side test, plane intersection, inside test with the polygon's own normal), `CheckHits` (up to 32 hits sorted by distance), `CheckHitVertical`, `CheckWidth` (radius 5, eight probes: two diagonals, x, z; wall = |ny| < 0.5), `GetFootPoly` (ray 15 down), `MoveCheck`. Quirks kept: the headroom probe adds vel.x to BOTH x and z; the first CheckHit of MoveCheck is a first-hit query (t1 = 0), mask comes straight from the caller (1 for everybody, 8 for Osmond). `tools/dc/validate_move.py` uploads random polygon sets + random positions/velocities (half of them stood right at floor edges) to PCSX2, calls the game's `MoveCheck` and `CheckHit` through the hook mailbox and compares: **~1,600 MoveCheck cases and ~19,000 CheckHit segments, 0 mismatches** (tolerance 2e-3).
- **Walking** (`walk.*`, validated by `tools/dc/validate_walk.py`): per tick (60/s) the free-move branch of `MoveChara`: stick (raw bytes, `AxisCalibration` dead zone 50, /128) rotated by the camera angle (`angle_h = atan2(-dir.x, -dir.z)` of the camera), times `run_speed` = 1.45; vertical velocity -= 0.1 per tick (min -10, zeroed when grounded); facing by `unitRotation` (15 degrees per tick toward `atan2(vx, vz)`); animation by `keyCtrl` (0 idle, 1 run when |lx|+|ly| >= 0.85, 2 walk; speed = 0.8 * (0.1 + max(|lx|,|ly|)), cap 0.7); then `MoveCheck` with the 3x3 cells around the player.
- **Camera**: follow point = pos + displacement*7 (x, z), y = pos.y + disp.y*2 + 7.5 (per-character DAT_01dc2764) + 6; right stick adds height (-ry, capped 30) and angle (0.04 * -rx), shoulder buttons +-2 degrees/tick, "behind" button; `autoCamTrial` = ray from the camera ref toward the camera (80 long) against the camera pieces of all cells within 240 of the camera (CheckHits mask 0), `CameraAutoMove` (shrink distance to the hit, swing the angle), vertical check keeps the camera >= 25 above camera polygons, distance/height easing (near 10, far 80, up_near 60 read from the live game; distance is measured from the CCharacter object, which still holds the PREVIOUS tick's position), sideways auto-turn from the stick while running; then `CCameraFollow::Step` (angle eased by `AngleInterpolate` mode 1 with divisor max(1, speed/2); next pos = follow + (D sin a, H, D cos a); speed 8 smoothing in `CCamera::Step`) at the end of the tick (`motionDrive`).
- **Lock-step verification rig**: the hook stub (`coop/hooks.py`) got a GATE (+8) and step tokens (+0xC): with the gate set the stub keeps serving the mailbox and returns to the game only when a token is available, so a tool can freeze a frame, read state, inject input and release exactly one frame. `validate_walk.py` patches the four CGamePad stick getters (0x12B310/340/2B0/2E0) to read injected ints from RAM (restored afterwards), records player position and the whole camera object per tick for a scripted input sequence, then replays the same inputs through `dcwalk.exe` from the recorded start state. Results (300 ticks each): circle, mixed (right stick + changing stick), cam (right stick swings), wall (running into walls and back) and up (385 units through rooms/corridors): **worst deviation 0.0005-0.0114 units for the player and 0.002-0.017 for the camera** (float rounding; positions are ~1600 units from the origin).
- **Helper**: `tools/dc/reset_game.sh` restarts PCSX2 and reloads save state 1 (the test floor); needed after long test runs (the player walks onto stairs/events and the game leaves free-move).
- Not ported yet: lock-on, first-person view, damage/knock-back, events (doors, chests, stairs), monster collision push, `GetEventPoly`, water/healing zones, treasure box collision. Per-character parameters (`follow_height`, `mask`) are defaults for Toan.

## Milestone 4 (monsters, combat): monsters + monster damage verified against the running game (2026-10-19, in progress)
- **Script VM** (`dccore/script.*`): the game's `CRunScript::exe`; one bytecode for dungeon events, town events and monsters (`.stb`). Instructions are {op, a, b}; 8-byte slots {type 0 int/1 float/2 string/3 pointer, value}; ext call args: `a` slots incl. the function id; results are written through pointer slots (`SetStack` only writes the value bits, the slot keeps its type). Monster entry functions: 1 init, 100 main loop, 110 flinch, 120 death, 50 revive. `tools/dc/stbdis.py` disassembles (ids come from the three ext tables 0x2918A0 / 0x26B310 / 0x269C50).
- **Monster table / floor layout / placement**: see `dccore/tables.*`, `monsters.*`. `ArrangementPos` (15 monsters) verified 15/15 against the game for several seeds, **including the init scripts**: SetupViewMonstor runs function 1 as each monster is placed (it may move the monster, e.g. flyers go to y=21, and may use rand()), so later candidates are measured against the moved positions. The distance tests of ArrangementPos are real 3D `DistVector`s.
- **CMonstorUnit::Step port** (`dccore/monster_ai.*`, `monster_combat.cpp`): per awake monster (state 2): CheckViewLevel (wake within `clip_level` = 300, at most 4 awake unless last floor), hit-box registration + CheckDmg, script (flinch 110 / death 120 start a new run and resume in the same tick; else function 100 resumes each tick, restarted when it finishes), knock-back, `MoveCheck2` / `MoveChecMonster` (stop when walking into the player / another monster), movement with `CheckHit` (+5 head offset, 10-unit probe), `CheckWidth`, `CheckHitVertical` (130 down from +10) with gravity -0.2 only when `fall` and above the floor, bounce of `dir.y`, turning by `AngleInterpolate` (mode 0: fixed step), motion time (`CCharacter::Step` + `SetMotionEX`: blend 10 ticks at step 0.1 with phase matching for motions 1/2, `+2` frames, flags 1 freeze / 2 hold / 4 restart; `dccore/motion_state.*`). **Traps found**: (1) `MoveCheck2/MoveChecMonster/CheckHitUser` measure the distance with `uStack_xx = 1.0` stores that land on the y lane of an array declared with 4 bytes, i.e. y is overwritten and the distance is **horizontal only**; (2) monsters gather collision with `setCollisionData(30, 5)`: floor polygons of the 3x3 cells filtered by a box (+-30, +-150, +-30), then (only for scripts and `CHK_MOVE_INFO`) other awake monsters' stand-in prisms (`dun/etc/atrcol.mds`, scaled by 0.2 * radius, box +-80 high); the movement tests use the terrain list only; (3) the hold flags of `motionDrive` (`driveStepHold | CMonUnitHold`) skip a whole Step (`+0x98` pause flag; next Step restores the last motion, DrawMonstor freezes motions while paused or hit-stopped); (4) the game draws the monster (motion step, world position of the registered hit spheres) after Step, so hit spheres seen by Step(n) come from draw(n-1); (5) some memory a monster slot holds from an earlier monster (floor height) affects the first ticks (`height` before the first vertical probe).
- **libm**: the game's `sinf/cosf/atanf/atan2f` are fdlibm float versions run on the EE FPU; `dccore/libm_ps2.*` ports them operation by operation and matches the live game bit for bit (`validate_libm.py`, 3000 random inputs per function). All monster/walker/script-VM code uses them now.
- **Hit boxes** (`dccore/combat.*`): `NowColData` pool of 96 spheres (`CCollisionData::Set`, 0xa0 bytes: centre, damage, radius, life, target mask 1 player / 2 monsters, kind 3 = knock-back, element/effect flags, owner kind (0..5 character, 200+5*slot monster), sub id, slayer table, kick-back), upkeep in `motionDrive` (cooldown, life--, radius growth). Monsters register body spheres (`SET_BODY_COL`, per-character damage percents `SET_BODY_COL_PARA 10..15`) and attack spheres (`SET_DMG_COL` + `SET_DMG_PARA(damage, flags, type[, angle])`) on bones of their model (world position from the pose at the drawn frame; matches the game within ~0.85 units, max near motion changes).
- **CheckDmg port** (`monster_combat.cpp`): player/shot sphere touches a body sphere -> guard frames, element/status effects, damage = `(dmg [x1.5 close / falloff for ranged owners]) - defense (Ruby half)`, element bonus `(0.004 * element points + 0.005 * magic) * dmg`, resist %, slayer table (`+0.015/point`), per-character % of the body sphere, Xiao/others can be "no flinch" (return 0), instant-kill chance, poison (10% of max life every 180 frames) ... returns 0/1 (script 110)/2 (script 120). Loot at death: weapon exp event, stolen gold, rare item, `SelectAttach`, gold `base + base*rand/2` with the 2x/0.5x flags. **Verified** with `tools/dc/validate_dmg.py` (writes a hit box into the game's `NowColData` on a monster's body sphere at chosen ticks and in the port): life, state, script position, status counters equal for plain, element, status-effect, ranged and killing hits; the ~224-250 extra `rand()` draws the game makes at a hit are hit-mark/particle effects, not logic. Gold/item amounts of a drop are NOT compared yet (the death script's effects use rand() before the loot code).
- **Player model**: `UserStatus` is kept in the game's byte layout (`user_status.h`: character at +4, floor +2, life +0x12, max life +6, defense +0x4348, weapon slots 0xf8 bytes at +0x450c + 0xaa8 * character, weapon id/attack/durability/element at +0/+4/+0x10/+0x16..); `tools/dc/snapshot_status.py`-style dump via `validate_dmg.py` (`work/user_status.bin`). Toan starts with weapon 257, then 299, 314, 331, 347, 363 for the others (`defWeapon`).
- **Rigs**: `tools/dc/validate_monster.py` (monster movement/AI lock-step), `validate_dmg.py` (damage). ## Exact arithmetic of the real game (measured in PCSX2, 2026-10-19)
Everything that steers scripts (target points ~2200 units from the origin, float ulp 2.4e-4) needs the last bit right, so the arithmetic was measured instead of assumed (`validate_fpu.py`, `validate_vu.py`, `validate_vu_axis.py`, `validate_libm.py`; all single instructions/functions run inside the game via the hook mailbox on random operands):
- **EE FPU** (`gamemath.h`): `mul.s` truncates (round toward zero), `div.s` and `sqrt.s` round to nearest, `add.s/sub.s` align the smaller operand to the larger one with ONE guard bit, add exactly, then truncate to 24 bits (fits 6000/6000 samples; plain truncation or plain nearest both fail). `gm::fadd/fsub/fmul/fdiv` implement this.
- **VU0 library helpers** (`sceVu0Normalize`, `DistVector`): every add/sub/mul/div/sqrt truncates; normalize = `s=(x*x+y*y)+z*z; q=RZ(1/RZ(sqrt s)); out=RZ(v*q)`; distance = `RZ(sqrt((dx*dx+dy*dy)+dz*dz))`, `d = b - a`. 2000/2000 random vectors + 5000 axis-aligned ones match (`vu_normalize`, `vu_dist` in `monster_ai.cpp`, helpers `gm::vadd..vsqrt`).
- **Script VM**: float `+ - * /` use the EE model, sin/cos opcodes use `ps2_sinf/cosf` (before, a 1-ulp difference in a script-computed target changed `sceVu0Normalize` of a 1-D vector between 1.0 and 0.99999994 and drifted the monster by one ulp per step).
- Result: `validate_hurt.py 1000 12345 --near 0 --dist 30` (monsters + player damage + death + game over) is now identical for all 1000 ticks (monster positions, hit spheres, player life/mode/motion); a second arrangement (seed 777, slot 3) matches except a 0.004 drift of one monster after 600 ticks (not found yet; probably ground height / floor_y rounding in `check_hit_vertical`). `validate_monster.py` beyond ~90 ticks diverges only because that rig does not model the player being hit (the real script leaves its loop when the monster hits the player).
- Rig caveat: `validate_dmg.py` with its default `--dist 120` puts the player outside the map (he falls, feed becomes garbage); use `--dist 30`.

## Milestone 4, monster shots (CSHOT_EFFECT) verified against the running game (2026-10-20)
- **Data**: `BtEntryEffectTbl` (0x27FA70, 34 pointers) -> 0x70-byte rows (`ShotDef`): +0x00 name (effect model `dun/effect/<name>.chr`, whose config file is `<name>.cfg`, not base.cfg), +0x10 mode (0 flies, 2 stays put), +0x14 look-at, +0x18 speed per phase (4 floats), +0x28 sphere radius per phase, +0x38 range in ticks, +0x3c damage, +0x40 effect bits, +0x44 kind (3 = knocks the player back), +0x48 target mask (1 player, 2 monsters), +0x4c motion per phase (4 shorts, -1 none), +0x54 type (100 = bomb at the end: `SetBombEffect` sphere radius 20 * scale, life 45 * scale, kind 3), +0x58 bomb scale, +0x5c bomb damage. A monster table entry names up to two shots (+0x68, +0x6a).
- **Phases**: 0 start (model motion 0, holds the last frame), 1 flight (motion 1, loops; moves by the velocity every tick, range counter), 2 hit (motion 2), 3 end of range (motion 3); a phase ends when the effect's motion time is within the last frame (`end-1 <= t <= end`, the motion clock is `CCharacter::Step` run in the draw after the logic step). Each tick in phases 0/1 `checkCollision(radius, ...)` looks for the player (distance of the player's PREVIOUS position + height table <= radius + 6 -> 2), then monster hit spheres (3), then terrain (`CheckHit` first hit over polygons within +-20/30 of the shot -> 1); the damage sphere (`CCollisionData::Set(radius, 1.0, pos, damage, life 2, target, kind, effect bits, 0)`) is put at the hit point (or the shot's position); type-100 shots end in a bomb sphere at once when the hit phase has no motion.
- **Script side**: `_SET_SHOT(frame, x, y, z [, damage])` / `_SET_SHOT2` register the muzzle frame and the aim point; when the monster is drawn the frame's world position is read (state 2) and the next `Step` of the unit fires the shot from there toward the aim point.
- Code: `dccore/shots.*`, `MonsterWorld::fire_shots / shot_collide`, `MonsterBase::shot_*`; the shot step runs in `step_effects()` (after drops), the motions in `step_shot_motions()` (draw part, after the logic). ## Boss check (2026-10-19)
Goal: make sure every boss can be reached and beaten. Method: `work/boss_check.py` (a bot that steers to the nearest living monster body sphere and swings; Ruby / ranged characters keep the lock-on button held and shoot from afar; all monsters at 1 hp so that reachability and the hit rules decide; `--god` keeps the hero alive), plus the new harness tools of `play.gd`: `--bot [--bot-range N --bot-lock 1]`, `--cols 1` (every monster's body spheres that are on, with world positions and windows, and `HITSTATS`: the smallest gap between a player sphere and a body sphere that was open, and the closest a boss sphere came to the hero), `--event-end 1` (where the hero stood when the last script event ended), `--boss-hp N --boss-hp-all 1 --boss-hp-keep 1`, `--game-int i,v`, `--game-flag a,b`, `--polys x,z` (collision walls of a cell), `dccoll <iso> <stem> 1 6 <map> 0 0 --fixed-frames` (frames and objects of a boss room).
Bugs found and fixed:
- **The boss rooms never ran their own scripts**: the hero started at the room's `in` frame, the gate / key-pedestal markers (d04 moon / sun keys + event 403, d05 events 404 / 405, d01's horn) were never active and the intro scenes were skipped. Now `DcModels::assemble_walker` gives boss rooms a `DungeonSession` and runs their floor-start function like story rooms (`DC_BOSS_HARDCODED=1` brings the old behaviour back for comparisons); the intro scene plays, the script spawns the monsters and places the hero, the gates work.
- **d06 stage 1**: the hero began at the arena's centre (0, 0, 0) where the boss's shock wave (`c17_syougeki`) landed at once; the intro leaves him at (0, 0, 48.32) facing the boss.
- **d03**: the `in` frame lies behind a wall (z = 220) that cannot be crossed; function 100 puts the hero at (0, 10, 150).
- Hard-coded fallbacks for the same places are in `DcModels::assemble_walker` (`kStarts`: d03, d04, d06 stage 1, d07) for `DC_BOSS_HARDCODED`.
Results of `boss_check.py 12000` (script-driven rooms): cleared by the bot: d02 (Toan), d03 (Ruby), d05 (Toan, flag 29 = the door key), d06 stage 1 (Ruby), d06 stage 2 (both, flag 41 + int 10 = 2), d07 (both). Not by the bot: d01 (the fight is on the hill / plateau (y 45..99) above the arena floor and the bot cannot find the ramp; the earlier hand tests cleared it from the hill), d04 (the bot stops at the key pedestals / the door scene, then at c15b), d03 / d06 stage 1 with Toan (see below).
Facts about the fights that the check showed: **d06 stage 1 is a ranged fight** - the arena's dais is fenced by a low wall at z = 12.6, the boss's head (weak point `dcol00`, radius 4, only open in frames 10..34 / 60..165 of its attack motions, y about 50, z about -65) cannot be reached with a sword; Ruby, Osmond (and probably Xiao) shoot it with the lock-on. The hands (`c17b`, `c17c`, 3200 hp each, body sphere only open in frame 9..10 of their motion) must die first (the head's spheres appear when both are dead). **d03**: the barrier `baria` (100 hp) has to be broken first, then `c13a` (700 hp, spine sphere radius 4.5); the boss walks away from melee attackers (Toan did not catch it, Ruby killed it).
Not checked live: all of this is from the port's own rules (the rules themselves were verified against the game earlier); a comparison run in PCSX2 would be needed to prove the fights feel right.
Test hint: `--god` refills life every 20 ticks and sets invulnerability, which also stops chests and markers from reacting (`free` needs `invuln == 0`): use it for fights only.
